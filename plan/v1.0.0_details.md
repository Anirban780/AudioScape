# AudioScape v1.0.0 Codebase Audit & Architectural Details

This document contains a comprehensive synthesis of the AudioScape codebase audit findings, system details, architectural weaknesses, security issues, and critical bugs identified during the initial code review. Use this document as the single source of truth when onboarding new developers or starting a new agent session.

---

## 1. Codebase Folder Structure & Layout

The project is structured as a split client/server monorepo:

```
/backend
  /config       - Firebase Admin initialize and YouTube credentials
  /controllers  - Controller handlers (track, firestore, recommendation)
  /routes       - Express routing modules
  /services     - YouTube data proxy, Firestore CRUD helpers, Gemini keywords
  server.js     - Entry point, CORS config, route mounting
  recommend.js  - Pure JS TF-IDF recommendations engine
  test.js       - Stale/exploratory manual verification script (untracked DB interactions)

/frontend
  /components   - Layout features, lists, and playback components (Player, Home, Auth)
  /pages        - View entry points (Home, Explore, Favorites, Playlists, Profile, Landing)
  /store        - Zustand stores (usePlayerStore, usePlaylistStore)
  /context      - React Context providers (AuthContext, ThemeProvider)
  /utils        - Local Firestore API wrappers, YouTube queries, genres/keywords helpers
  /firebase     - Client-side SDK initialization config
  App.jsx       - Eager routing configuration, global state layout mounting

/utils          - Shared shadcn/ui components (lives at root level, outside /frontend)
  /components   - Shadcn primitives (button, card, dialog, dropdown, input, etc.)
  /lib          - shadcn utility helper (cn class merger)
```

## 2. Configuration & Path Alias Mismatch

There is a fundamental discrepancy in path resolutions among the three configuration files:

1. **`vite.config.js`**: Defines `@` as `./utils` and `utils` as `./utils`.
2. **`jsconfig.json`**: Defines `@/*` as `./*` (project root) with overrides mapping `@/components/*` to `utils/components/*` and `@/utils/*` to `utils/*`.
3. **`components.json`**: Uses `@/utils/components/ui` for the components alias.

### Effective Inconsistency
Because Vite compiles `@` as `./utils`, a component-level import like `@/components/ui/button` resolves to `./utils/components/ui/button` at runtime. However, `components.json` is configured expecting `@` to mean the project root, leading to double nesting bugs (`./utils/utils/components/ui`) if shadcn tries to add components automatically.

## 3. Dependency Audit & Duplication

The root `package.json` contains several misplaced backend dependencies that are bundled with the Vite frontend.
* **Duplicated Backend Dependencies in Root**: `express`, `cors`, `express-rate-limit`, `python-shell`, `textarea`, `openai`, `natural`, `stemmer`, `dotenv`.
* **Duplicate AI SDKs**: Both `@google/genai` (modern) and `@google/generative-ai` (older) are listed in the root `package.json`.
* **Backend Truth**: The backend has its own `package.json` inside `/backend` containing its correct runtime dependencies. The root dependencies should be cleaned up to prevent build bloating and package confusion.

## 4. Critical Bugs & Security Vulnerabilities

### A. Auth Bypass on Recommendation Endpoint (`recommendationController.js`)
* **Endpoint**: `POST /api/music/recommend`
* **Vulnerability**: The controller accepts a raw `userId` in the JSON request body and processes recommendations for that user ID without validating the caller's request token or session status. Any user can pull another user's history and recommendations by guessing/enumerating Firebase UIDs.

### B. Auth Bypass on Related Tracks Cache (`trackController.js`)
* **Endpoint**: `POST /api/music/cache-related-tracks`
* **Vulnerability**: Accepts `keyword` and `tracks` array and writes directly to the shared Firestore cache collection (`relatedTracksCache`) with zero auth checks. A malicious caller can poison this cache, affecting the recommendations engine for all users.

### C. Recommendation Timestamp Calculation Bug (`recommendService.js`)
* **Location**: `recommendService.js:7` calling `recommendSongs()`
* **Vulnerability**: The recommendation engine signature in `recommend.js` is:
  ```js
  recommendSongs(userHistory, relatedTracks, currentTimestamp, topN = 10)
  ```
  However, `recommendService.js` invokes it as:
  ```js
  recommendSongs(userHistory, relatedTracks, topN)
  ```
  This passes `topN` (typically `10`) as the `currentTimestamp`. Inside `recommend.js:7`, this breaks the recency calculation (`currentTimestamp - song.lastPlayedAt`), treating every single song in the history as if it was played in 1970 (infinitely old) and decaying its weight to `0`.

### D. Client-Side YouTube API Key Exposure (`youtube.js` & `ExplorePage.jsx`)
* **Location**: `frontend/utils/youtube.js`
* **Vulnerability**: Calls the YouTube Data API directly from the browser using `import.meta.env.VITE_YOUTUBE_API_KEY`. This compiles the key directly into the client bundle, exposing it to anyone viewing browser developer tools. ExplorePage queries this exposed utility directly.

### E. Unprotected Gemini AI Key Route (`validateKeywords.js`)
* **Endpoint**: `POST /api/extractKeywords`
* **Vulnerability**: Hits the Gemini 1.5 Flash API with no rate limit or authorization checks. Furthermore, the history is interpolated directly into the system prompt via `JSON.stringify(history)`, exposing the system to prompt injection.

## 5. Architectural & Design Smells

### A. Shell Duplication (Shotgun Surgery Risk)
* `Home.jsx`, `ExplorePage.jsx`, `FavoritesPage.jsx`, and `PlaylistsPage.jsx` all copy-paste ~40 lines of identical JSX wrapping:
  ```jsx
  <div className="h-screen flex ...">
    <Sidebar />
    {isSidebarOpen && <MobileDrawer><Sidebar/></MobileDrawer>}
    <div className="flex flex-col flex-1 overflow-auto ...">
      <ResponsiveLayout>
        <TopNavbar>{MenuButton, SearchBar, ThemeToggle, UserMenu}</TopNavbar>
        {/* page content */}
      </ResponsiveLayout>
    </div>
  </div>
  ```
* Any change to the navbar, drawer, or sidebar requires editing all four files independently.

### B. Firestore N+1 Query Patterns (Collection Scans)
Throughout the client-side Firebase utility scripts (`frontend/utils/api.js` and `frontend/utils/playlists.js`), database queries fetch the entire document collection and filter/update in memory instead of utilizing Firestore query filters:
* **`saveLikeSong`**: Pulls the entire user `music_history` collection to locate the document matching `track.id` via a `.forEach()` loop.
* **`removeLikeSong` / `fetchLikedStatus`**: Employs the same full scan pattern.
* **`fetchUserLikedSongs`**: Fetches all history documents, then filters `liked === true` using JavaScript array filters.
* **`addSongToPlaylist`**: Performs a full denormalized copy of the track metadata into the playlist's array, causing data consistency issues if track information changes.

### C. Dead / Stale Code
* **`MusicPlayer.jsx`**: Unused playback player left over from earlier iteration; imports volume state variables that do not exist in `usePlayerStore.js` and is not referenced anywhere in active layouts.
* **`ProfilePage.jsx`**: Stale page relying on `localStorage` for track history and favorites with comments to "replace with Firestore later". This directly duplicates the Firestore-backed `FavoritesPage.jsx` functionality.
